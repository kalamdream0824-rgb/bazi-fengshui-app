# 经典命例兼容测试 v1

> 状态：已建立首组结构兼容测试
> 范围：八字原局结构与财富事实提取
> 不属于：现实准确率、人物经历核验、未来预测验证

## 1. 测试目的

这套测试回答一个有限问题：当前后端面对古籍明确记录的四柱时，能否保留原文强调的结构差异，并产生可追溯的财富证据。

测试通过不表示古籍判断真实，也不表示系统可以准确预测个人经历。古籍案例在这里是传统规则兼容夹具，不是现实金标准。

## 2. 为什么直接使用四柱

许多古籍命例没有能够独立核验的公历时间、地点与现代时区口径。测试不反推或伪造公历生日，而是直接使用原文四柱：

```text
古籍四柱 → 十神与藏干重建 → 现有原局分析 → 财富事实提取
```

公历转四柱、节气边界与真太阳时继续由既有 `BaziServiceTest` 和 `contracts/fixtures/bazi-cases.json` 验证。两类测试不得混为一体。

## 3. 首组命例

来源：《滴天髓阐微》公开数字转录本，通神论·寒暖章的成对命例。

| 编号 | 四柱 | 原文结构摘要（转述） | 当前引擎结果 | 判断 |
|---|---|---|---|---|
| `ditiansui-summer-fire-wet-earth` | 癸丑·戊午·丙午·壬辰 | 丑为湿土，能缓和夏火并保存部分金水条件 | 旺衰 3.0，中和 | 方向兼容 |
| `ditiansui-rentieqiao-summer-fire` | 癸巳·戊午·丙午·壬辰 | 年支换成巳后火势增强，金水条件减弱 | 旺衰 4.0，偏强 | 方向兼容 |

两个命例均能提取：

- `natal.combination.output_wealth`
- `natal.combination.wealth_capacity`
- `natal.combination.peer_wealth`

这同时暴露了现有模型的不足：它能识别宽泛的十神共存，却尚未表达湿燥、合化是否成立、藏干力量、阳刃及制化关系。因此目前只能称为“相对方向兼容”，不能称为完整复现。

## 4. 来源等级

当前两例标为 `C`：有公开可定位的古籍转录文本，但人物经历、生辰来源与版本传承未完成独立交叉核验。

后续等级统一为：

- `A`：原始版本或可靠影印可定位，生辰和关键经历另有独立史料；
- `B`：古籍来源可定位，生辰或经历至少一项获得确交叉来源；
- `C`：仅有可定位的传世文本或数字转录，适合规则兼容，不适合准确率统计。

任何等级都不能仅凭一条命例证明某条规则普遍成立。

## 5. 运行方式

在后端目录执行：

```bash
./mvnw -q -Dtest=ClassicBaziCompatibilityTest test
```

测试覆盖：

1. 命例必须记录书名、版本、定位、链接和来源等级；
2. 四柱必须是合法干支；
3. 测试范围必须声明为 `STRUCTURAL_ONLY`；
4. 夹具不得把历史经历写成准确率断言；
5. 当前旺衰等级、分数和财富证据必须与人工审核后的映射一致；
6. 成对命例必须保留古籍明确强调的相对差异。

## 6. 新增命例流程

1. 先保存来源信息与四柱，不查看当前引擎输出；
2. 将古籍原断拆成结构、岁运、事件三个层次；
3. 只选择当前引擎确实有能力表达的结构项；
4. 人工写出古籍主张到内部字段的映射理由；
5. 先运行测试观察失败，再决定是模型缺项、规则冲突还是古籍口径不同；
6. 不得为了让单个古籍案例通过而直接修改全局权重；
7. 新增案例先进入开发集，另留未参与调参的保留集。

## 7. 下一阶段

建议扩充顺序：

1. 同一章节中的成对反例，优先检查单一结构差异；
2. 有明确大运顺序但不依赖具体公历年份的命例；
3. 能以独立史料核验出生与经历的近现代案例；
4. 错配命盘与无命盘通用文案对照；
5. 在结果发生前冻结的前瞻样本。

只有第 3—5 类进入受控盲测后，才可以讨论现实命中率。
