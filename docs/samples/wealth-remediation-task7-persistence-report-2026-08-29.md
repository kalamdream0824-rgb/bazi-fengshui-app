# 财富整改任务 7：生成与快照保存交付记录

- 日期：2026-08-29
- 范围：财富通俗版后端 `wealth-narrative-v3` 正式生成、生成失败处理、版本化保存与读取。
- 不在本任务：前端阅读适配、真实 MySQL 容量验证、全量浏览器回归、支付和会员权益、提交推送与部署。

## 交付结论

任务 7 已完成后端接入。新生成的财富报告不再保存 v2，而是通过完整出生排盘、三年年度上下文、v3 判断、年度比较和正文许可校验生成 `wealth-narrative-v3`，校验通过后才保存。

这不是前后端闭环完成。当前前端仍只识别财富 v2；任务 8 完成前，不应让用户用现有页面验收新报告。当前持久化测试使用 H2，也不能代替任务 9 的真实 MySQL 验证。

## 实现范围

1. 新增 `WealthReportGenerator` 业务边界及默认实现，正式串联 `WealthV3Analyzer`、`WealthNarrativeWriter.plan` 和 `validateDraft`。
2. 财富入口按 `Asia/Shanghai` 取得 `asOf`，产品固定生成从该年开始的连续三年；内部二至五年能力不对客户端开放。
3. 正文使用独立版本 `wealth-narrative-v3`，并保存：
   - `asOf`
   - `zoneId = Asia/Shanghai`
   - `horizonYears = 3`
   - `calculationVersion = wealth-path-v2`
   - `policyVersion = wealth-expression-v1`
   - `copyVersion = wealth-plain-v3`
4. 生成上下文同步保存分析日期、年限和三种版本标识，便于审计；客户端提交的旧财富上下文不参与 v3 内容选择。
5. 内容校验失败统一返回 `WEALTH_CONTENT_INVALID`，并验证数据库中不产生报告。
6. 读取按已保存 `contentVersion` 分流：财富 v3 读取 `WealthNarrativeV3`，财富 v2 读取原 `WealthNarrativePlan`，旧 v1 保持原结构。未知版本返回 `REPORT_CONTENT_VERSION_UNSUPPORTED`，不默认套用事业模型。
7. 历史读取不运行 v3 生成器或校验器，不静默改写旧 JSON。

## TDD 过程与缺陷证据

先改测试再改业务代码，并实际观察到以下失败：

- 正式生成测试期望 `wealth-narrative-v3`，实际仍返回 `wealth-narrative-v2`。
- 契约测试期望后端已实现且正式 `ReportInfo` 引用 v3，实际仍标记为未实现草案。
- 生成器抛出内容校验异常时，接口最初返回通用 500，而不是稳定的内容错误。
- 读取未知内容版本时，旧逻辑尝试按事业模型反序列化，产生 500。

实现后分别补齐正式 v3 生成、稳定错误码和显式版本分流；没有通过修改断言隐藏上述失败。

当前 JDK 环境下，Spring 测试初始化时 Mockito 的 inline mock maker 自附加失败，测试尚未进入业务断言。测试资源中改用 subclass mock maker 后，失败处理集成测试能够正常运行；该设置只影响测试，不进入生产代码。

## 未完成与下一步

1. **任务 8：前端版本分流与阅读。** 当前 `reportApi.ts` 和财富阅读页面只认识 v2。必须增加 v3 类型与独立渲染，正确处理无主线、并列、空风险、观察事项和未知版本。
2. **任务 9：真实存储和系统回归。** 当前 `content_json` 是 `TEXT`，样本三年紧凑 JSON 最大约 51,559 UTF-8 字节，但抽样不是所有合法输入上限。必须在真实 MySQL 的实际字符集和字段类型下验证保存/读取，不能因 H2 通过就判定容量安全。
3. 前端接入后再运行全量前后端测试、构建和浏览器生成/刷新/回看/账号隔离。没有实际触发远程 CI，不能宣称 CI 通过。
4. 本任务没有修改表结构、迁移历史数据、重启验收环境、提交、推送或部署。

任务 7 解决的是“新版后端能否可靠生成并保存，旧报告会不会被改写”。它不证明命理规则具有现实预测准确率，也不替代用户对正文价值和中文阅读体验的审核。
