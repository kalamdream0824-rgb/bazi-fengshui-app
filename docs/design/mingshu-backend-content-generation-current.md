# 命书后端内容生成逻辑说明

- 更新时间：2026-08-29
- 核对版本：2026-08-29 任务 9 工作树（财富 `wealth-narrative-v3` 已完成前后端与真实 MySQL 系统验证）。
- 适用范围：当前“生成命书 → 保存 → 读取”后端流程，以及财富 v3 页面和真实存储的已验证边界。
- 目标读者：产品负责人、后端开发者，以及需要评审当前实现的其他智能体。

本文最初基于任务 7 代码核对整理，现已同步任务 9 结果。财富 v3 已完成后端生成、快照、前端阅读和真实 MySQL 三年样本系统验证；字段容量和现实准确性仍有明确边界。

## 1. 一句话结论

当前命书由“排盘计算＋人工设定的规则与权重＋预先编写的文案组合”生成，没有接入 LLM，也不是每次重新创作一篇文章。

系统已经能够依据命盘和年度条件选择内容，但尚未做到每一段结论都严格由该用户、该年份的充分依据决定。

必须区分三个概念：

| 概念 | 当前含义 | 不能等同于 |
|---|---|---|
| 排盘数据 | 历法计算得到的干支、十神、大运等 | 已验证的现实事件预测 |
| 规则证据 | 满足某条判断规则的命盘条件 | 对用户真实经历的调查或验证 |
| 分数、置信等级 | 代码设定的权重、阈值和判断等级 | 赚钱概率、恋爱成功率或统计准确率 |

在相同有效输入、分析年份及代码版本下，内容选择是确定性的，不靠随机抽取文案制造差异。报告编号、生成时间等元数据另行产生。

## 2. 当前入口与输出范围

### 2.1 接口

- `POST /api/v1/reports`：登录后生成并保存报告。
- `GET /api/v1/reports`：读取当前账号的命书列表。
- `GET /api/v1/reports/{id}`：读取当前账号的一份已保存报告。

生成请求包含出生信息、主题、版本，以及对应主题需要的状态信息。后端通过 `BaziService` 重新排盘，不直接使用前端已经展示的解读结论。

旧的报告预览与渲染代码仍存在，但不是本文所描述的页面命书主流程。不能把旧预览功能当成当前产品已经开放的功能。

### 2.2 主题、年限与版本

| 主题 | 当前年限 | 额外输入 | 后端新生成内容版本 |
|---|---|---|---|
| 事业 | 生成当年及下一年 | 当前状态、目标、近期体感 | `career-narrative-v3` |
| 财富 | 生成当年起三年 | 无需财富问卷 | `wealth-narrative-v3` |
| 感情：单身 | 两年计算，今年详细、明年简短 | 单身状态 | `relationship-single-v1` |
| 感情：交往中、已婚 | 生成当年起三年 | 当前关系状态 | `relationship-narrative-v1` |
| 综合 | 当前页面生成不支持 | — | — |

这些年份是按生成当年起算的年度范围，不是未来连续十二个月，也没有按月预测。财富 v3 以服务端 `Asia/Shanghai` 分析日所在年份为起点，产品入口固定三年；内部结构支持二至五年，但不向客户端开放年限参数。

财富前端当前仍只识别 v2。后端已生成 v3 不等于页面已可验收；任务 8 完成前，新财富报告可能无法被现有阅读页正确解析。

财富和感情当前仅开放通俗版。事业虽然接受专业版选项，但正文仍使用同一套 `CareerNarrativePlanner`，没有按版本生成实质不同的内容，不能视为已经完成独立收费的专业版产品。

## 3. 总体执行流程

```text
校验账号、主题、版本和状态输入
                ↓
重新排盘，构建原局与逐年数据
                ↓
        按主题进入不同分析流程
        ├─ 事业：规则匹配 → 去重排序 → 年度判断
        ├─ 财富：事实提取 → 五路径评分 → 独立判断 → 年度比较 → 正文校验
        └─ 感情：事实提取 → 五维度分析 → 重点、风险与跨年变化
                ↓
根据判断结果与用户场景选择文案分支
                ↓
组合结构化正文，写入版本快照
                ↓
前端阅读；再次打开时读取原文，不重新生成
```

总入口为 `ReportService.create`。三个主题共享部分排盘和年度数据，但不是共用同一套判断与正文生成逻辑。

## 4. 公共计算层：系统先知道什么

### 4.1 原局与年度数据

`BaziService` 计算四柱、十神、藏干、大运等基础数据。`AnnualContextFactory` 以生成当年为起点，逐年整理：

- 流年干支、流年天干相对于日主的十神及其功能组。
- 该年度所在的大运。
- 流年地支与原局各柱、大运之间的关系。
- 原局十神分布、日支、旺衰粗判等结构化条件。

这些信息随后由各主题事实提取器或规则引擎使用。并非排盘界面上展示的每个字段，都已参与命书判断。

### 4.2 旺衰是简化的加权判断

当前 `ReportAnalysis.scoreBalance` 主要计算生扶分：

- 月令生扶日主：加 2 分。
- 年、日、时地支生扶日主：每项加 1 分。
- 年、月、时天干与日主同类：每项加 1 分。
- 上述天干生日主：每项加 0.5 分。
- 总分不少于 4 为偏强，不多于 1.5 为偏弱，其余为中和。

这是工程上明确可复查的粗判，不是完整的格局、调候、制化、特殊格局综合算法。基础分类发生偏差时，依赖它的下游规则也会受到影响。

## 5. 三个主题分别怎样形成结论

### 5.1 事业：规则匹配，再结合问卷解释

执行链：`ThreeYearAssessor` → `AnnualPeriodAssessor` → `AnnualRuleEngine` → `CareerNarrativePlanner`。其中 `ThreeYearAssessor` 是历史名称，当前事业实际使用两年。

主要步骤：

1. 根据年度条件匹配事业规则。
2. 每条规则至少需要两条去重后的依据；这里按证据键去重，并不代表统计意义上的独立证据。
3. 存在反向依据时，降低规则的置信等级。
4. 按优先级、置信等级和规则键排序，同类结果去重，每年最多保留两项机会与两项压力。
5. 综合保留结果，判断该年偏向进取、准备、谨慎、变化还是平稳。
6. 结合问卷，将结论解释为岗位、求职、自营或学习场景。

正常完整输入还可命中“流年十神组＋旺衰”的基础规则，避免没有特殊组合就完全没有解读。但这只是基础覆盖，不代表每个年度都有突出事件；通用引擎中的无结果兜底分支仍然存在。

问卷不改变排盘、规则命中和基础年度阶段，主要改变解释场景、行动建议与观察事项。当前正文的一些总论、建议还会直接按身份、目标及年份序号选取，因此不能把所有文字都视为个体命盘推导。

### 5.2 财富：同时计算五条路径

五条路径为：稳定收入、靠能力赚钱、项目和额外收入、合作带来的收入、把钱留下。

`WealthFactExtractor` 提取原局明现与藏干十神、部分原局组合、大运、流年和地支关系；`WealthPathEvaluator` 为每条路径累计正负权重，同一路径内同一证据键只计一次。

以下为代码中的部分权重示例，不是完整规则表：

| 条件 | 对路径的影响 |
|---|---|
| 原局明现正财 | 稳定收入 +3，留钱 +1 |
| 流年正财 | 稳定收入 +4，项目收入 +1，留钱 +1 |
| 流年食神或伤官 | 能力收入 +4，项目收入 +1 |
| 流年或大运带动财星，同时旺衰偏弱 | 留钱 -3 |
| 财富被带动，同时出现冲、刑或害 | 合作收入 -2，留钱 -2 |

v3 保留上述旧事实与原始权重，但不再直接使用旧版“总得有一个主方向和一个风险”的裁决结果生成正文。`WealthV3Analyzer` 对每年五条路径分别保留支持和限制，再由表达策略决定：

- `quiet`：没有正负依据，只能说明本规则未形成具体判断。
- `supportive`：有支持、没有限制。
- `restricted`：有实际限制、没有支持。
- `mixed`：支持和限制并存，两面都必须呈现。

表达强度与倾向分开。净分高不自动升级为强结论；较强表达还要求至少两组互不重复的已核实根事实。相对排名第一但支持很弱时，不再包装成“最旺钱路”。多个方向相当时允许并列，全部不突出时允许没有主线。

风险只从实际负向依据产生；无负向依据时风险为 `null`。相邻年度比较支持、限制、规则和根事实的真实变化，条件相同就承认延续，不按“第一年、第二年、第三年”制造剧情。

`WealthNarrativeWriter` 根据判断和年度比较生成确定性通俗正文，并在保存前重新校验模板许可、引用范围、年份、表达强度和覆盖。校验失败返回 `WEALTH_CONTENT_INVALID`，不保存报告。这里的表达约束不能证明原始命理权重具有现实预测准确率。

### 5.3 感情：分别计算有利因素、不利因素和突出程度

五个维度为：认识与连接、交流回应、日常相处、关系边界、长期稳定。

`RelationshipFactExtractor` 将原局、大运、流年和日支等条件映射到这些维度。配偶星采用当前设定的传统男女取法：男取财星组、女取官杀组；这是现有算法口径，不代表覆盖所有现实关系结构。

每个维度分别累计：

- 支持权重：正向权重之和。
- 限制权重：负向权重绝对值之和。
- 突出程度：支持权重＋限制权重。
- 净倾向：支持权重－限制权重。

因此，一个维度既有明显机会又有明显压力时，仍可能成为最值得关注的重点，不会简单正负抵消后就不再展开。

正文语气分为无明显因素、偏有利、偏有压力、有利与限制并存。主次重点按突出程度选择；风险只从存在负向依据的维度中选择，没有负向依据时不生成风险段落。

关系状态不进入基础事实提取和评分，同一命盘同一年度不会因为用户选择单身或已婚而改写计算结果。状态改变的是适用场景和产品年限。

相邻年度会比较支持、限制及依据来源的变化，不仅比较总分。两年没有明显差别时承认延续，不通过随机换词或预设剧情制造变化。

单身新版只用今年的结果决定今年总论和重点；明年最多简述两项重要维度变化，不让明年判断覆盖今年结论。

## 6. 正文如何组织出来

正文不是直接展示全部计算数据，而是按照主题、主次方向、倾向、风险、关系状态或事业问卷选择分支，再组合成结构化内容。

主要文案来源：

- 事业：`CareerNarrativePlanner` 内的条件分支，以及年度规则配套文案。
- 财富 v3：`WealthPlainCopyV3` 的闭合文案分支与 `WealthNarrativeWriter`；旧 `report/wealth-plain-v2.yml` 只服务历史 v2 生成逻辑和兼容测试。
- 感情：`report-copy/relationship-plain-v1.yml`，配合年度比较和单身专用组织逻辑。

例如，“交流回应方面有利”会选择对应的有利表述；存在较强限制时使用另一分支。聊天、邀约、付款、准备作品等生活化例子是预先编写的解释或建议，不是系统发现用户已经经历了这些事情。

## 7. 保存与再次阅读

生成成功后，`ReportService` 将账号、主题、版本、出生输入、场景输入、结构化正文及生成时间保存到 `bazi_report`。

再次查看时，按账号归属和报告编号读取快照，并按内容版本解析。当前逻辑不会因为算法更新或年份变化而自动改写旧报告。

不同主题保存的计算细节不完全相同。财富 v3 正文保存每年根事实、计分依据、五路径判断、年度比较以及文字块引用，并记录 `asOf / zoneId / calculationVersion / policyVersion / copyVersion`；生成上下文另存分析日期和产品年限。事业与感情的审计粒度仍不完全相同，因此不能把财富 v3 的可追踪性理解为全主题已经统一。

读取按已保存的 `contentVersion` 选择模型。财富 v1、冻结 v2 和新 v3 均保留独立读取；历史读取不重跑当前生成器或校验器。未知版本返回 `REPORT_CONTENT_VERSION_UNSUPPORTED`，不默认按事业结构解析。

当前生成流程仍属于不扣费联调，没有完整接入单份支付和会员每日生成额度。能生成、能保存不代表商业权益已经实现。

## 8. 已确认的局限

| 局限 | 当前代码表现 | 对输出的影响 |
|---|---|---|
| 旺衰和权重属于简化设定 | 生扶计分、固定加减分和阈值 | 可复现不等于现实预测准确，仍需规则审校与校准 |
| 事业部分内容主要依赖问卷 | 总论、行动和部分说明按身份、目标、年份序号选取 | 不同命盘可能得到相近建议 |
| 财富 v3 系统验证仅覆盖测试输入 | 任务 9 已完成 69 项财富和 35 项通用浏览器检查，含 12 组完整出生测试输入 | 测试链路通过不等于现实预测准确或所有输入均已覆盖 |
| 财富 v3 的 MySQL `TEXT` 余量偏小 | 13 份三年报告已原样往返，最大 51,559 字节，占 `TEXT` 上限约 78.7% | 当前样本通过不等于所有合法输入或五年内容容量安全 |
| 财富原始规则尚未做现实校准 | v3 改善来源追踪和表达许可，但沿用旧事实与权重 | 文字更克制不等于预测准确性已被验证 |
| 三个主题的质量门槛不一致 | 感情已区分支持、限制和无风险，其他主题尚未全面采用 | 不能把感情模块的改善当成全主题都已完成 |
| 专业版差异未完成 | 事业选项不改变正文规划，财富和感情未开放 | 尚不能按两个成熟独立内容产品理解 |

此外，技术支持五年不等于五年产品内容已打磨完成。财富 v3 内部二至五年共用同一年度不变量，但正式契约和页面仍限制三年；若扩大产品年限，还需要重新评审摘要长度、阅读布局、存储体积和产品价值，不能只改参数。

## 9. 后续建议与验收方向

财富任务 4–9 已完成固定剧情、强度、无风险、来源绑定、前端阅读和当前三年测试样本的系统验证。下一步不应继续增加后端文案，而应进行人工体验验收并保留存储风险：

1. **任务 10：整理体验验收。** 对照有利、受限、混合、无风险、并列和无突出方向等实际输出，列出遗留问题后再决定是否推广到其他主题。
2. **治理存储容量。** 正式放量或扩至五年前，用正式迁移将 `content_json` 调整为 `MEDIUMTEXT`，并增加序列化字节上限测试；不能把当前 13 份样本保存成功当成容量证明。
3. **继续人工审读弱信号样本。** 结构完整和测试通过不等于内容达到付费价值；不能靠提高语气强度掩盖原始信号不足。
4. **另立算法治理批次。** 旺衰、权重和现实准确性需要独立审校与校准，不应混入前端接入任务。

验收不能只检查接口返回成功、页面能显示或文案变得顺口；还要检查正文是否超出了其依据能够支持的范围。
