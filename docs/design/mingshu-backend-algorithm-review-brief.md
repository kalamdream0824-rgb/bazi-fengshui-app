# 命书后端算法瓶颈与外部智能体评审简报

> 文档状态：外部评审输入稿
> 更新时间：2026-08-23
> 适用范围：命书报告后端内容引擎，不讨论 UI、支付渠道和 PDF 视觉样式
> 目标读者：需要在不了解本项目历史的情况下，对算法架构、规则覆盖与内容质量提出建议的智能体或工程师

## 1. 评审目标

本项目正在开发一套以传统八字结构为输入、生成主题型文字报告的后端引擎。当前已经完成确定性排盘、年度规则匹配、通俗版/专业版呈现和文字型 PDF，但内容质量尚未达到正式付费标准。

本次希望外部评审重点解决以下问题：

1. 如何在不编造结论、不降低证据纪律的前提下，保证每个有效命盘、每个报告年度都有明确主题结论。
2. 如何将目前少量、离散的布尔规则改造成可扩展、可解释、可校准的年度趋势算法。
3. 如何正确处理支持证据、反向证据、大运调制及多条信号之间的冲突。
4. 如何让通俗版与专业版共享计算结果，同时产生真实的信息价值差异。
5. 是否需要引入大模型；如果需要，它应位于哪个环节、受到什么约束。

## 2. 最新产品约束

以下是当前已经明确或正在收敛的产品要求：

| 项目 | 要求 |
|---|---|
| 首发主题 | 综合、事业、财富、感情 |
| 报告版本 | 通俗版 ¥6.9；专业版 ¥12.9；两份报告独立购买 |
| 时间粒度 | 按年，不做按月预测 |
| 时间范围 | 当前代码输出三年；最新方向拟缩为两个年度 |
| 内容组织 | 主题贯穿，不能只是几个无关年度段落的拼接 |
| 无命中 | 不接受将“证据不足”“继续观察”作为付费正文交付 |
| 已生成报告 | 可以自由下载 |
| 会员额度 | 每天最多生成 3 份，超出后允许单独付费 |
| 合规边界 | 传统文化解释，不承诺确定事件，不替代医疗、投资、法律或现实决策 |

需要特别说明：缩短为两个年度可以提升内容密度，但不会自动解决单年度无规则命中的问题。当前代码仍按“生成当年及随后两年”计算。

## 3. 当前系统不是大模型生成

目前内容完全由后端确定性规则生成，不调用 LLM，也不随机拼接。

```text
前端选择主题和版本
        ↓
PaipanRequest
        ↓
BaziService 重新排盘
        ↓
AnnualContextFactory 提取逐年结构化事实
        ↓
AnnualRuleCatalog 提供对应主题的 7 条规则
        ↓
AnnualRuleEngine 布尔匹配、证据过滤和排序
        ↓
ThreeYearAssessor 聚合年度结果
        ↓
PlainReportPresenter / ProfessionalReportPresenter
        ↓
ReportDocument
        ↓
Apache FOP 生成文字型 PDF
```

因此，当前“像胡说八道”的感受主要来自规则覆盖不足和固定文案重复，而不是模型产生了幻觉。

## 4. 当前年度事实模型

`AnnualContextFactory` 目前能够提供以下信息：

- 流年干支；
- 流年天干相对日主的十神；
- 流年十神所属五类功能组：生扶、同类、表达、财富、责任；
- 当前大运及大运天干功能组；
- 命局旺衰粗分：偏弱、中和、偏强；
- 原局是否出现不同十神功能组；
- 流年地支与年、月、日、时四柱地支之间的合、冲、刑、害等关系；
- 流年地支与大运地支之间的关系；
- 下一年流年天干功能组。

其中以下两个维度对任意有效命盘年度都必然存在：

```text
流年功能组：5 种之一
命局承载状态：3 种之一
```

理论上二者可以形成 `5 × 3 = 15` 种穷举基础状态，但当前规则引擎没有建立这层完整映射。

当前缺失或没有充分建模的维度包括：

- 流年、大运与原局之间的完整天干关系；
- 藏干透出、强弱及岁运变化；
- 地支关系发生在不同柱位时的主题权重；
- 大运对每个主题的基线增益、压制或转向；
- 多条关系之间的制化、抵消、组合和优先级；
- 可复核的格局、调候、喜忌或用神体系；
- 用户现实状态，如职业类型、是否在职、收入结构、婚恋状态等。

这些缺失导致系统能够识别部分结构信号，但很难将其收敛成具体且持续的主题答案。

## 5. 当前规则模型

四个主题各有 7 条年度规则，共 28 条。每条规则包含：

- 规则键；
- 所属主题和类别；
- 机会或压力类型；
- 年度阶段；
- 优先级；
- 初始置信等级；
- 若干必须同时满足的证据组；
- 固定标题、结论、行动和现实观察信号。

匹配逻辑可简化为：

```text
for rule in topicRules:
    if 所有证据组都至少命中一个事实:
        evidence = 去重后的支持事实
        if evidence 数量 >= 2:
            接受规则

按优先级和置信度排序
同一类别只保留第一条
机会最多保留 2 条
压力最多保留 2 条
```

这是一种硬布尔门槛：一条规则要么完整命中，要么完全不产生信息。系统没有部分得分、接近命中、基础趋势或候选信号的概念。

## 6. 已测得的覆盖率问题

项目使用 36 组代表性命盘进行诊断，覆盖不同出生年份、月份、日期、时辰和男女取法。每个主题检查 36 份报告、108 个年度结果，四个主题共检查 432 个年度结果。

| 主题 | 无规则结论年度 | 年度无结论率 | 至少一栏为空 | 无真实反向证据 | 36 份报告中至少一年无结论 |
|---|---:|---:|---:|---:|---:|
| 综合 | 14/108 | 13.0% | 92/108（85.2%） | 108/108（100%） | 8/36 |
| 事业 | 32/108 | 29.6% | 97/108（89.8%） | 108/108（100%） | 20/36 |
| 财富 | 14/108 | 13.0% | 92/108（85.2%） | 108/108（100%） | 11/36 |
| 感情 | 4/108 | 3.7% | 66/108（61.1%） | 108/108（100%） | 4/36 |

该样本不是用户分布意义上的统计模型，但足以证明问题是系统性的，尤其是事业主题。

## 7. 核心瓶颈

### 7.1 P0：规则集合不是完备集合

每个主题只有 7 条条件规则，且没有一条承担“主题基础态”的职责。因此无法保证所有命盘年度至少命中一条规则。

把三年缩成两年只能减少暴露次数，不会改变单年度无命中的概率。若不调整规则结构，两个年度仍可能出现一个或两个年度全部无命中。

### 7.2 P0：严格门槛与完整覆盖之间缺少中间层

“至少两项独立证据”本身是合理的证据纪律，不应简单降低成单证据命中。但当前只有强条件规则，没有稳定存在的基础判断层，导致系统只能在以下两种结果间二选一：

- 命中强规则并给出结论；
- 完全没有结论。

真正缺失的是“始终可计算的基础趋势 + 强规则增强”两层模型。

### 7.3 P0：无命中被包装成付费内容

当前没有规则通过时，系统创建 `INSUFFICIENT_EVIDENCE` 年度结果，并写入：

- “现有证据不足，先观察再判断”；
- “当前未形成两项以上相互独立的规则证据”；
- “保留关键事件记录”；
- “出现连续信号后再调整计划”。

这些内容随后进入总览、年度章节、行动路线和专业版方法说明，形成多次重复。技术上的保守失败被当成正式内容交付，这是当前最直接的付费质量缺陷。

### 7.4 P0：反向证据模型存在接口，但实际始终为空

`AnnualRule` 和 `FactAnnualRule` 支持 `counterEvidence`，但 `AnnualRuleFactory` 创建所有业务规则时固定传入空的反向选择器列表。

因此当前 432 个年度诊断结果中，真实反向证据均为 0。专业版仍然输出“未检出反向事实”，但这不是计算后的发现，而是没有配置过反向规则。

### 7.5 P0：呈现模板强制补齐空栏目

某个年度可能只命中机会或只命中压力，但报告结构固定要求展示两栏。缺失一侧时会写入“暂无达到证据门槛”等占位内容。

这会把“该年度主要呈单边倾向”错误表现成“系统不知道答案”。呈现层应按真实结果条件展示，不能为了版式对称强制填空。

### 7.6 P1：三年聚合只是拼接，不是跨年推理

`ThreeYearAssessor` 当前主要完成：

- 拼接三个年度阶段标签；
- 组合年度标题；
- 去重后取前三条行动建议。

它没有分析：

- 哪一年是主题主导年；
- 哪一年是转折点；
- 前一年如何为后一年形成条件；
- 信号是增强、减弱还是改变方向；
- 跨年冲突应如何解释。

所以“主题贯穿”目前更多是章节命名和标题重复，不是一个真正的时间序列结论。

### 7.7 P1：规则之间只有排序，没有推理关系

当前规则结果按优先级排序、按类别去重，但规则之间不存在：

- 相互支持；
- 相互冲突；
- 抵消；
- 放大；
- 前置条件；
- 因果或阶段关系。

这导致多个信号同时出现时，系统只能保留优先级更高者，而无法解释为何保留、为何降级以及另一条信号去了哪里。

### 7.8 P1：置信度不是校准概率

当前 `HIGH / MEDIUM / LOW` 主要由规则作者预先指定；有反向证据时再机械下降一级。它不是根据历史样本、专家标注或统计结果校准得到的置信度。

因此该字段只能理解为“规则内部等级”，不能解释为事件发生概率，也不应向用户暗示统计可信度。

### 7.9 P1：专业版没有独立的分析深度

通俗版和专业版共享同一份年度评估。专业版主要增加：

- 规则键；
- 完整证据；
- 反向证据区域；
- 置信等级；
- 方法边界和规则索引。

由于反向证据为空、来源体系尚未建立，专业版目前更像调试日志扩写，没有增加新的推理维度，难以支撑更高定价。

### 7.10 P1：规则没有完整来源和审校治理

现有规则能通过键名追踪到代码和文案，但没有为每条规则记录：

- 典籍、版本、章节和页码；
- 属于古籍直接表达、现代推导还是工程经验；
- 所属流派及与其他流派的差异；
- 审核人、审核状态和修订记录；
- 适用范围和已知反例。

这使规则扩充很容易变成“增加更多听起来合理的断语”，而不是可审计的知识工程。

### 7.11 P1：测试保护结构，不保护付费内容价值

当前测试能够验证：

- 排盘和年度事实是否生成；
- 规则门槛与排序是否符合代码预期；
- PDF 是否可以生成和提取文字；
- 主题词是否出现在报告中；
- 低证据结果不能标记为高置信。

当前没有系统测试：

- 付费正文不得出现无答案占位语；
- 每个年度必须有明确主题结论；
- 结论必须具有两项真正独立的依据；
- 反向证据必须来自真实配置；
- 同一空泛句不能跨章节重复；
- 三年或两年必须形成时间轨迹；
- 专业版必须增加新的信息价值；
- 规则在大样本中的覆盖率、冲突率和偏向分布。

### 7.12 P2：缺少现实上下文，限制了结论具体程度

命盘结构不能知道用户当前是否在职、是否创业、是否单身、收入来源或实际目标。相同的结构信号在不同现实状态下可能对应完全不同的表现。

如果报告要求进一步具体到“晋升、跳槽、创业、结婚”等事件，单靠现有出生信息无法保持严谨。需要在以下方向中作出产品选择：

- 继续只输出结构趋势和现实观察信号；
- 在生成前增加少量主题问卷；
- 输出分支场景，而不是断言唯一事件。

## 8. 当前最困难的技术与内容矛盾

### 8.1 保证有答案，不等于保证强结论

产品要求不接受无命中，但算法不能为了覆盖率把弱证据包装成强结论。需要区分：

- 基础年度倾向：由必然存在的结构事实得出，保证完整覆盖；
- 强化结论：只有满足额外独立证据时才出现；
- 反向条件：明确什么因素会削弱或改变结论。

### 8.2 规则越多，不代表内容越可靠

盲目增加规则可以提高命中率，也会增加冲突、重复和不可解释性。必须同时建立来源、优先级、冲突关系、适用范围和回归样本。

### 8.3 命理流派差异无法靠代码自然消失

旺衰、格局、调候、喜忌等方法存在不同流派。若不明确采用的体系，算法会混合互不兼容的判断依据。外部建议应说明采用的理论边界，而不是只提供更多规则。

### 8.4 LLM 可以改善语言，但不能补足事实

当前直接接入 LLM 的主要风险是：它会把“事实不足”改写成更流畅、更确定的故事，放大付费内容的误导性。

如果未来使用 LLM，原则上只能：

- 接收后端已经确认的结构化事实、候选结论和禁止项；
- 在限定 JSON Schema 中做归纳、比较和语言转换；
- 不得创造新命盘事实、规则键、事件和时间点；
- 输出后必须经过事实引用校验和确定性质量闸门；
- 保留模型、提示词、规则和内容版本。

## 9. 待评审的候选架构

以下仅为候选方向，不是已经决定的最终实现：

```text
有效命盘
   ↓
确定性年度事实
   ↓
主题基础状态（穷举覆盖，保证有主结论）
   ↓
大运、柱位和关系调制
   ↓
强条件规则增强
   ↓
支持/反向/冲突证据合成
   ↓
两年度时间轨迹
   ↓
付费质量闸门
   ↓
通俗版 / 专业版呈现
   ↓
可选：受约束的语言模型润色
```

一个可评估的基础状态方案是：

```text
5 种流年功能组 × 3 种命局承载状态 = 15 种基础状态
```

四个主题可共享状态计算，但使用不同的主题解释映射。大运、流年地支关系和原局结构作为修正项，而不是决定是否“有答案”的唯一门槛。

需要外部评审判断：

1. 15 状态是否过粗，是否需要加入大运功能组形成更高维但仍可控的状态空间。
2. 应采用离散等级、加权分数还是规则图谱。
3. 基础状态如何产生至少两项真正独立的证据，而不是同一事实的重复编码。
4. 如何避免四个主题只是对同一基础状态换词复述。

## 10. 明确不接受的伪解决方案

以下方案不能作为正式解决办法：

1. 把证据门槛从两项降成一项，只为提高命中率。
2. 保留固定兜底段落，但把“证据不足”换成更好听的措辞。
3. 无条件调用 LLM，让模型自行补齐年度答案。
4. 仅增加 PDF 页数、术语和规则键来制造专业感。
5. 强制每年同时输出机会和压力，即使其中一侧没有真实结果。
6. 用随机文案变体解决重复感。
7. 直接复制开源项目的喜用神、格局或权重规则，而不验证流派与适用边界。

## 11. 希望外部智能体回答的问题

请外部智能体尽量基于当前约束给出可实施回答，而不是泛泛建议增加 AI 或增加规则。

### 11.1 核心算法

1. 怎样设计一个对有效命盘年度“总有定义”的主题基础判断函数？
2. 15 种基础状态是否足够；如不足，最小还需增加哪些维度？
3. 强规则、基础趋势和反向证据应该如何合成？
4. 规则冲突采用优先级、分数、规则图还是其他方式更合适？
5. 如何定义证据独立性，避免两个事实其实来自同一源信号？

### 11.2 两年度时间序列

1. 报告缩成当前年度和下一年度后，如何形成真正的趋势关系？
2. 应输出“延续、增强、转折、回落”等哪些可计算轨迹？
3. 在临近年底生成时，应使用今年和明年，还是明年和后年？

### 11.3 内容质量

1. 如何自动识别空泛、重复、无答案和主题偏离？
2. 如何定义通俗版与专业版的实质差异？
3. 专业版应披露到什么程度，才能兼顾可追溯性和可读性？

### 11.4 校准与验证

1. 在没有科学意义上的真实标签时，应如何校准规则权重和置信等级？
2. 专家审校、历史案例和用户反馈分别应该承担什么角色？
3. 回归样本需要覆盖哪些边界；合理规模是多少？
4. 哪些指标可以作为付费上线的硬门槛？

### 11.5 LLM 边界

1. 当前阶段是否应该完全不使用 LLM？
2. 若使用，最安全的输入、输出 Schema 和校验机制是什么？
3. LLM 应只负责语言转换，还是可以在结构化候选之间做排序与综合？

## 12. 建议的验收目标

以下指标可作为外部方案设计时的最低目标：

- 有效命盘的付费报告生成后，两个年度均有明确主题主结论；
- 付费正文中“证据不足”“继续观察”等无答案占位语为 0；
- 每个年度结论至少关联两项可展示且来源不同的依据；
- 没有机会、压力或反向证据时，隐藏对应区域，不填充固定句；
- 两个年度必须标明延续、增强、转折或回落关系；
- 每份报告指出主导年度、主要风险和可验证现实信号；
- 专业版增加来源、推理链、冲突解释、反向条件和方法边界，而不是只增加篇幅；
- 使用至少 200 组代表性命盘建立覆盖、冲突、重复和边界回归集；
- 任何生成失败必须发生在扣费或消耗会员次数之前。

## 13. 预计改动范围

若采用“基础状态 + 强规则增强”的方向，主要涉及：

| 模块 | 预计变化 |
|---|---|
| `AnnualContextFactory` | 扩充事实、来源和调制信息 |
| `AnnualRule` / `FactAnnualRule` | 增加基础分、反向选择器、来源和适用范围 |
| `AnnualRuleFactory` | 不再固定传入空反向证据 |
| `AnnualRuleEngine` | 从纯布尔过滤升级为基础状态、强规则、冲突和降级合成 |
| `ThreeYearAssessor` | 改为两年度评估并增加时间轨迹推理 |
| `YearAssessment` | 区分基础判断、增强结论、反向条件和质量状态 |
| Presenter | 条件展示；专业版增加真实推理价值 |
| YAML 资源 | 增加基础状态文案、规则来源和版本信息 |
| 测试 | 增加覆盖率、冲突、重复、质量闸门和大样本回归 |

排盘服务、PDF 技术框架和大部分前端页面不需要推翻重做。主要风险集中在后端内容模型、规则治理和验收样本，而不是接口或渲染技术。
